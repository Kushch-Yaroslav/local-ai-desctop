# Hardware-safe context estimate

The context selector shows the backend/model-supported limit separately from an observed loaded context and a hardware-safe estimate. A supported limit or a successfully loaded context is not a prediction that a larger context will fit.

`src/shared/context-estimator.ts` is the pure budget calculation. `src/main/services/context-estimate.ts` collects active runtime evidence and parses explicit llama.cpp startup allocation lines. When the log contains final model, compute, output, target/draft KV, draft/MTP, recurrent-state, and vision-projector allocations for both memory tiers, context/slot counts, target and speculative KV precisions, and the caller supplies explicit host and device reserves, the service can estimate presets using measured KV bytes/token:

`weights + KV bytes/token × context tokens × sequence slots + speculative weights/buffers + reserve`

The service uses live remaining RAM/VRAM plus logged current allocations as the memory budget, so measured target/draft weights, compute, output, recurrent-state, and vision-projector allocations are counted once. It scales only observed target/draft KV allocations per token and measured draft compute buffers per explicit draft slot. Missing categories, unknown placement, missing cache precision, missing recurrent/SSM allocation evidence, unavailable or invalid hardware snapshots, missing vision evidence, or absent reserve values block extrapolation. A known configuration that cannot fit even its smallest supported preset reports `0`, not a false safe value. An allocation log is usable only when its selected model path and final loaded context match the live runtime evidence; it is never used to extrapolate to another model, context size, or configuration. A minimal log can still show a backend-confirmed active context as **observed**, with extrapolation honestly marked unknown.

The renderer requests `window.localAi.contextEstimate(modelId): Promise<RuntimeContextEstimate>`. The IPC handler selects the active backend/model and calls `collectRuntimeContextEstimate` with configured maximum/presets, `getHardwareStats()`, matching backend evidence, the allocation log, and reserve values. Normal launches default to an 8 GiB host reserve and a 2 GiB device reserve. `LOCAL_AI_CONTEXT_HOST_RESERVE_BYTES` and `LOCAL_AI_CONTEXT_DEVICE_RESERVE_BYTES` may raise these minimums using integer byte counts; malformed, unsafe, or lower-than-default overrides are reported as an invalid reserve and suppress the estimate. The host reserve guards against unmeasured prompt caches and runtime/OS growth; it is not an independent measurement of those consumers. The default llama log is `paths.logs/llama-cpp-mtp-server.log`, overridable with `LOCAL_AI_LLAMA_SERVER_LOG`; the launcher exports the actual log path to Electron.

The backends expose `getRuntimeContextEvidence(modelId)`: Ollama reports the matching loaded model's `/api/ps` context and optional total/VRAM residency; llama.cpp reports active `n_ctx`, `n_ctx_train`, and `meta.size` for its active model. The UI keeps training metadata separate from the configured model/backend limit and loaded context. Runtime `meta.size` is displayed as model metadata, not resident VRAM. Ollama's reported resident bytes likewise must not be treated as weight-only sizes or added again to process usage. Ollama does not expose cache allocation/precision/slots or reserves, so it currently provides observed context only.

For the supplied 32K runtime, the live endpoint reports `n_ctx=32768`, `n_ctx_train=262144`, and model metadata `size=16799719424`. The matching verbose allocation log records one target and MTP slot, f16 target/draft KV, target weights and KV, draft KV/compute, recurrent-state buffers, target/draft compute, host projector weights/compute, and output buffers. The estimate uses the live free-memory snapshot, adds back the allocations of the currently loaded server to reconstruct a baseline budget, and subtracts explicit reserves. The result is capped at 32K, the loaded context evidenced by the log. Neither the 262K train context, the app's 131K configured ceiling, nor the model metadata size makes 64K/128K safe. The initial nonverbose 16K log lacked allocation sizes and precision and supported observed context only. A subsequent verbose 16K launch supplied complete evidence, yielded a 16K estimate, and completed real Chat and Agent requests. Reusing the 32K log against that 16K runtime yielded no hardware-safe estimate. Vision/projector placement and prompt-cache allocations remain configuration-sensitive: the projector reservation is included, while host cache/other unmeasured consumers are guarded by the conservative host reserve.
