## Findings and decisions

| Area | Previous assumption | Result |
| --- | --- | --- |
| Application/data root | Personal mounted project directory | Module-relative application root; XDG user locations; keep an existing source runtime/data lineage in place. |
| llama.cpp | Personal CUDA build directory in Bash | Existing settings API extended with validated UI-owned executable/model/GPU placement configuration. Legacy adjacent build remains an optional fallback. |
| Model/projector files | Three personal absolute GGUF paths and a fixed selector | One versioned runtime-settings file now stores the live model registry. Migration seeds the three stable built-in IDs and overlays legacy paths; users can add, edit and remove arbitrary GGUF profiles without changing those IDs. |
| Rust bridge | Debug helper relative to shell CWD | Source helper rooted at the application; installed helper in Electron resources; explicit existing helper override retained. |
| Source launcher | Personal APPDIR/cache/PATH and mandatory Google Chrome helper | Rooted launcher, existing PATH/XDG environment retained, optional trusted sandbox fallback. No `--no-sandbox`. |
| Packaged launch | No runtime supervisor/production installer | Main process owns the existing supervisor and stops it on quit; parent-exit monitoring; no startup model allocation. |
| npm | Personal cache path | Standard npm cache; pinned lockfile, Node 24 and npm 10/11 expectations. |
| Linux packaging | No packaging tool/configuration | Pinned electron-builder; x86-64 `.deb`, desktop entry, runtime dependencies, static Rust helper; `--publish never`. |
| First run | Models/binary assumed present; setup action was easy to miss | Highlighted, keyboard-accessible «Настроить модели» action; setup opens once on an incomplete fresh install, can be dismissed persistently, and observes reduced-motion preferences. |

`/proc` process checks, standard Linux Chromium sandbox helper locations and
NVIDIA discovery are intentional system paths, not personal installation paths.
User-selected workspace paths are deliberately absolute persisted selections.
GPU telemetry/Max Context still assume one NVIDIA GPU; that separate architecture
was not broadened here.

Historical validation documents contain developer paths. The obsolete one-shot
`scripts/migrate-ollama-baseline.py` also contains machine-specific/destructive
migration operations; it is not a public installer and is excluded from the
package. Historical records and unrelated scripts were preserved instead of
blindly replacing every absolute string. The README/screenshots were not rewritten.

## Configuration and compatibility

`runtime-settings.json` is the one persisted source of runtime configuration,
exposed through the existing settings/preload API. Bash consumes shell-quoted
values generated by the same compiled resolver; it never evaluates the JSON file.
Runtime-owned selection request/state files remain the authority on the active
model. Saving settings does not claim a running server or reload a model.

The schema-v2 file holds the llama-server path, models directory, global GPU
placement, setup dismissal, and an array of model profiles with stable IDs,
display name, GGUF/projector paths, per-model GPU layers, tool support and MTP
mode. Legacy keyed path maps migrate idempotently into the three built-in stable
IDs without changing chat references or saved context discoveries. Custom IDs are
UUID-based; unknown models default to no tools, reasoning template or MTP and a
32K context ceiling. Paths support tilde expansion, relative paths, spaces and
apostrophes. Missing or moved server/model files remain saved and are surfaced as
readiness issues so users can correct other fields or dismiss setup. Explicit
files are parsed as GGUF before being accepted. Saves are atomic and private
(`0600`); malformed JSON is preserved as a timestamped backup when explicitly
repaired. Chats, evidence and project data remain in their existing SQLite/data
locations.

Fresh data/config/cache/log directories use XDG locations. An existing checkout
database selects its previous entire runtime tree; no evidence/database path
rewrite, schema migration, file deletion or automatic transfer occurs. An explicit
`LOCAL_AI_RUNTIME_ROOT` preserves the old override layout. Saved server paths take
precedence over environment defaults. SQLite conversations, context discoveries,
Agent evidence and Continue/Stop state keep their existing persistence behavior.

See [the installation guide](linux-installation.md) for exact locations, build
commands, setup and migration from an old checkout to an installed package.

## Packaging evidence

The host was Ubuntu 24.04.2 x86-64, Node 24.19.0, npm 11.17.0, Rust 1.94.1 and
Electron 39.8.10. `npm ci` and `npm run build` succeeded in a fresh source-only
directory with spaces, its own dependency installation/cache and no copied
`node_modules`, `dist`, runtime data or Rust target output. This is a same-host
clean-source build, **not** a fresh-OS compatibility claim.

Native helper inspection found a glibc 2.39 version requirement despite the
relevant symbols being weak. Packaging therefore uses the successfully built and
tested `x86_64-unknown-linux-musl` static PIE helper; development builds stay native.
The dependency-light Rust crate needed no source changes for that target.

A real Debian artifact was built:

- `release/local-ai-desktop_0.1.0_amd64.deb`
- Size: **163,135,172 bytes**.
- SHA-256: `911a0c0bef10a3d6904d6730bf0b9140377e15acbf7b85b81180d91cf44ced84`.
- Includes Electron, production application dependencies, compiled code and the
  static helper; excludes weights, user data and compiled test files.
- Installs to `/opt/local-ai-desktop/` while the desktop entry remains named
  Local AI Desktop. The archive contains a root-owned 0755 `chrome-sandbox`; the
  builder post-install script uses `unshare --user true` and selects root:4755
  only when user namespaces are unavailable. `--no-sandbox` is not used.
- `asar:false` is deliberate: the existing Bash supervisor invokes compiled JS
  from the ordinary filesystem. This avoids two copies of the configuration
  resolver/an unpacked secondary supervisor tree. Builder emits an advisory.
- Builder-generated Debian metadata/desktop entry/post-install sandbox and
  AppArmor handling were inspected. No installer script was run as root here.

An experimental AppImage was built during evaluation, then rejected as a supported
format: this builder's AppRun automatically appends `--no-sandbox` when its
namespace check fails. The supported Debian desktop entry does not do so. The
experimental artifact was removed; it is not a deliverable.

`scripts/linux-package-smoke.mjs` extracts the actual `.deb` into a temporary path
containing spaces and launches its shipped Electron binary with isolated data.
It verifies the preload API/SQLite/renderer, preserved built-in identities,
first-run setup auto-open/dismissal, reduced-motion behavior, manual setup entry,
custom GGUF readiness and registry persistence, quoted executable/model-directory
paths, CPU placement setting, restart persistence, idle state and owned-supervisor
shutdown. The shipped static helper generates a response through its real protocol
against a deterministic local SSE provider. No real weights or user conversations
are used.

Unprivileged extraction cannot reproduce the installer's root-owned sandbox helper
or AppArmor setup. The smoke uses the launcher's validated trusted system helper
in the temporary extraction and retains sandboxing. A real `apt-get install` was
attempted after confirming the package was absent, but this environment has no
privileged installer access (`/var/lib/dpkg/lock-frontend`: permission denied);
the host installation postinst was therefore not run. Archive contents and the
generated postinst were inspected directly. The package has not been claimed as
privileged-install tested.

## Remaining limits

- No privileged `.deb` install/uninstall or clean-OS/other-distro matrix was run.
- CPU/AMD/Vulkan inference and other NVIDIA cards were not newly benchmarked.
  Model placement defaults and NVIDIA-only measured context discovery remain.
- Configuring another file does not certify all of its architecture, tool-call,
  MTP tensor or projector behavior. Unknown models keep conservative controls;
  model-specific prompt templates and reasoning controls remain limited to the
  known profiles.
- No fresh real-model generation or GPU allocation was performed for portability;
  accepted model behavior is covered by existing regression suites and previous
  live validation, not claimed as a new hardware test.
- Optional browser/Agent external tools still require their own dependencies.
- The package version remains the repository's `0.1.0`; release versioning and the
  later README v0.2.1 pass are outside this feature. No release was published.
- Standard builder advisories about ASAR/dependency deduplication and Vite's large
  chunks remain; they did not fail builds or the packaged smoke test.
